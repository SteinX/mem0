# Mem0 检索质量 v2 实测

日期：2026-10-20（北京时间）。实现与隔离评测已完成；这是尚未部署的候选实现。

## 结论

固定留出集上，v2 方案首条命中率由当前默认不重排的 96.88% 提到 100%，
无答案非空率由 100% 降到 12.50%。相对于现有重排，首条命中率由 87.50%
提到 100%，完整请求 p95 从 1.818 秒降到 0.599 秒，降低 67.07%。

这不是“所有场景都更好”：全量 128 个正例上，v2 重排首条命中率为
96.09%，当前默认不重排为 93.75%；但路径和中文各比不重排少命中 1/32。
已有难例中的当前/历史、否定和主语归属仍有错误。保持新控制默认关闭，
将其作为可评测的选择，不能根据本轮结果全局开启。

## 数据与协议

128 个有答案问题、32 个无答案问题、512 条合成记忆。四类正例各 32 个：
中文规则、版本、路径、错误码。保留旧 P0 的 32 个问题，其中 err-05 收窄为
只询问 EACCES，避免原问题要求两个文档共同作答却只标一个答案。

开发集和留出集各 64 个正例、16 个负例。新增正例主题分离；部分负例项目名共享，
其问题/标识符留出。两组使用相同编写模板，因此这是受控合成回归集，
不能声称是盲测真实用户流量。门禁/凭据等内容均为夹具，没有生产记忆。

语料先审查再冻结，SHA-256：
284d4c1ef7e0c4feb9c839816b11de57b4d917dba8c2c3abe8dd93dc279aacd8。

两个隔离 PostgreSQL 存储按 fixture_id 排序后的文本、向量摘要完全一致，
各 512 条。插入顺序固定打乱，模型只接收记忆文本，不读取 fixture 标签。
仅复用本地 bge-m3 embedding；写入 infer=false，没有调用抽取 LLM。

四组每轮各跑 160 题，共两轮，1280 个计分请求，加 4 个排除的预热请求，
共 1284 个 HTTP 请求全部成功。重复增加时延样本，不增加独立质量样本数。
两轮每题正确答案名次完全一致。工具错误、未知标签、非空结果缺失或全零重排分数
均会中止评测；两套 Core 的重排失败/回退日志计数为 0。

基线为正式 Core v2.2.1-steinx.5-retrieval，源码
36e0b2cfe12c934ccab4f7dd4277e338e1d99e5c。候选复用相同不可变镜像，只挂载
三个 Core Python 源文件。Sidecar v0.3.15、MCP 0.1.9、模型权重和依赖均相同；
Core 同限 4 CPU / 6GiB，NLP=false。生产容器、配置和存量索引未用于实验。

每次请求 top_k=20、semantic threshold=0.1、explain=true。
MCP 扩取 60，Core 语义候选预算 240。基线最多重排 60 条；
候选先筛选标识符，再最多重排 20 条，之后按分数过滤，MCP 最终最多返回 20 条。
新方案的候选预算差异是被测改动的一部分，不能把收益全部归因于单一参数。

## 先调参，再验证

仅在开发集选定 exact_identifiers=true、rerank_candidate_limit=20、
rerank_min_score=0.05，然后固定参数才评估留出集，没有根据留出错误调高阈值。
开发集上，0.05 是所测网格中能消除负例非空、并保留 Recall@5 的最低分数阈值；
0.30 已使开发集 Recall@5 降到 98.44%。冻结选择与扫描结果见
[results-v2.json](results-v2.json) 的 selection_before_heldout。

另对基线开发集已有候选做离线语义阈值敏感性检查：仅将原 semantic threshold
提高至 0.60，负例非空仍为 50%；提高至 0.75 时 Recall@5 降到 78.13%。
该离线检查不是新的在线时延实验，未据此改动冻结方案。

## 延迟边界

同题同轮配对，平均“开启重排后的全链路增量”由约 1.30 秒降到 0.29 秒。
这是完整 HTTP MCP -> Sidecar -> Core 请求差值，包含检索、认证和序列化，
不是单独的模型耗时。新方案相对不重排仍有明显开销：
留出集 p95 为 0.599 秒，对比当前默认 0.147 秒。

所有请求串行执行，未做并发容量测试或独立冷启动剖析。
共享宿主和 embedding 服务可能影响时延，旧 P0 的时延不能直接与本次跨环境比较。
预热原始记录保留，但因实例已有状态不同，不作为公平的冷启动对照。

## 剩余问题

- 留出负例“Atlas 办公室门禁密码是多少”误命中凭据文件路径，重排分数约 0.621。
- “Helios 服务器在哪个物理机柜”误命中归档目录说明，分数约 0.0502。
- 开发集仍有 5 个首条错误：用户归属、被否定的旧提案、当前/历史版本，
  相同 deploy/.env 后缀的备份位置，以及蓝色部署入口/备份脚本。
- 精确匹配只检查常见 ASCII 路径和点分版本。多个同类标识符采用 OR 语义；
  它不推断否定、当前状态或哪个标识符才是问题目标，也不保证含空格/非 ASCII 路径。
  含斜线的表达会被当作路径，应只在明确标识符查找场景评估此控制。
- 仍从语义候选池筛选，不会将独立关键词命中并入候选，不回填历史索引。
- 重排分数不是答案存在的概率；不同模型需要独立评估阈值。
  Provider 内部合成回退分数仍按门限处理，需要监控失败日志；本轮未出现回退。

## 实现与验证

共享策略位于 mem0/configs/retrieval.py；同步和异步检索调用同一实现，
原阈值语义、作用域、过期/当前事实过滤及响应字段保持原契约。
三个新控制默认均禁用，不需要新的依赖或 REST/MCP 请求参数。

14 项新回归在旧实现上失败、2 项原行为用例通过；最终 47 项策略及同步/异步
专项检查通过，评测/分析工具的 9 项检查通过。Ruff/isort hooks、文档索引覆盖、
diff 空白检查通过。实际 BGE 推理与字段穿透由本次真实链路评测验证。

宽回归记录为 755 passed / 19 skipped / 3 failed；相同 3 项在未改动基线上
复现。其中 notice 的遥测开关修正后复跑通过；另两项 HF/SentenceTransformer
fallback 测试因精简 QA 镜像缺少 AutoTokenizer/CrossEncoder 可选依赖未通过。
未声称完整 suite 全绿；发布镜像中的真实 HF 推理另外通过。LSP 服务未安装。
